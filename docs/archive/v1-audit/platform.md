# V1 platform audit

## Evidence boundary

Inspected source commit `2bf6b5930858fdbb61bc388d4554d4657d9ce377` in the sibling v1 checkout. References below are repository-relative paths and one-based lines in that source. This is a code/configuration audit with an isolated backend test baseline, not a deployed-system penetration test or a successful production-build report. The source checkout was not executed or modified. A separate clean archive of this commit was later tested in a temporary Python 3.13.0 environment with the pinned requirements and resolver-selected transitive dependencies: 209 backend tests passed in 6.17 seconds. This does not establish real database, Firebase or deployment integration. Existing dirty/untracked files were excluded and left untouched. Documentation supplied orientation; code and current configuration determine the findings.

The [platform inventory](platform-inventory.json) assigns every file in this audit's scope a keep, rewrite or drop disposition. **Keep** means retain the tested behavior or evidence, subject to the new contracts; it does not mean copying a file unchanged. **Rewrite** means retain a useful responsibility with new boundaries. **Drop** means exclude from the v2 runtime or operating instructions. These are migration recommendations, not a Phase 2 architecture approval.

## Runtime and responsibility map

`backend/app.py:52` creates FastAPI, adds `/ping`, CORS and startup/shutdown hooks, then mounts market data, game, progression and user routers. Startup opens a PostgreSQL pool before initializing Firebase Admin (`backend/config/__init__.py:7`). Identity lives in Firebase; application profiles, curriculum configuration, completion summaries and quizzes live in PostgreSQL. Active connections, rooms and running engines live in Python process memory (`backend/services/game_service/router/router.py:56`). The market data service fetches Yahoo data through yfinance on demand (`backend/services/market_data_service/data_access/data_access.py:7`).

Useful boundaries already exist between routers, data access, content configuration and simulation. They should survive conceptually. Current HTTP handlers also call synchronous database/network functions directly; separation into files does not establish nonblocking execution or independent deployment.

## Identity and realtime contracts

REST token verification runs in `asyncio.to_thread`, requires a verified email and binds the authenticated UID rather than trusting client user IDs (`backend/common/auth.py:44`). Firebase initialization supports inline credentials, a credentials file or an explicit emulator configuration (`backend/config/firebase.py:24`). Application signup uses parameterized SQL and atomically creates the profile plus initial `module-1.1` progress row. UID conflicts return the existing profile; the database's lowercase-name unique index supplies username race protection (`backend/services/user_service/data_access/data_access.py:38`; `backend/config/database/init/01-schema.sql:11`). These are worth preserving as testable behaviors.

Both WebSocket endpoints accept the connection, require first message `{"event":"auth","data":{"token":"…"}}`, look up the application user, then emit `auth_ok` with UID. Missing/invalid authentication closes 4401; missing profile closes 4404. The next accepted control message is `start` with `level_id` and mode. Tokens are not put in URLs. Evidence: `backend/services/game_service/router/router.py:295`, `:343`; payload models at `backend/services/game_service/models/websockets.py:8`.

- `/game/single-player/ws` checks level availability before constructing an engine; denial emits `levelLocked` and closes 4403. It handles `registerOrder`, `nextTick`, `startTicking` and `cancelOrder`. Orders are stamped with the authenticated UID, client order IDs are reset, and quantities/order-specific prices are checked. Direct command responses and errors are raw objects, while engine events use the connection manager's envelope (`backend/services/game_service/router/router.py:351`).
- `/game/multiplayer/ws/{room_id}` checks authentication and room existence, then makes the first authenticated joiner the host. Subsequent `start` is host-only. It also accepts orders, cancellation, private messages, active-player requests and fake-news requests. No mastery gate appears before room/engine participation (`backend/services/game_service/router/router.py:426`).
- Engine messages use `{from:"server",event,data}`; private messages use `{from:<uid>,data:<message>}`. Multiplayer command replies add `Response`/`Error` suffixes. Sending schedules an independent task rather than awaiting delivery (`backend/services/game_service/router/connection_manager.py:26`; `backend/services/game_service/router/router.py:566`). The handshake and command responses acknowledge particular actions, but the inspected message model defines no protocol version, sequence, correlated delivery acknowledgement or idempotency key (`backend/services/game_service/models/websockets.py:8`).

The transport accepts orders without a written-plan field (`backend/services/game_service/models/websockets.py:30`). Tool toggles are not a substitute for prerequisite mastery: multiplayer tools default enabled, and the router explicitly distinguishes engine-enforced order constraints from presentation-only toggles (`backend/services/game_service/router/router.py:128`, `:278`). Learning/simulation internals are covered in the separate learning audit.

## Persistence, schema and resume

The schema defines profiles; levels and tickers; ticker metadata and reference portfolios; news/macro schedules and their ticker links; missions, tools and unlocks; level progress; achievements; activity events; and quizzes with per-user progress. Foreign keys, checks and several schedule-validation triggers provide useful consistency evidence (`backend/config/database/init/01-schema.sql:76`, `:141`, `:180`, `:199`, `:224`, `:411`, `:559`, `:604`, `:643`). Content/scenario details are audited separately; this schema is not a v2 content contract.

Level progress is one aggregate row per learner/level: attempted, completed, best points, attempt count and last-attempt time. Completion remains true once earned; best points only increase; the next level in the same module is inserted on completion (`backend/services/game_service/data_access/data_access.py:563`). Availability currently means existence of a tutorial progress row; all puzzles become available after `module-1.4` completion (`:654`, `:693`, `:728`). This is progression, not evidence of the new mastery dimensions. Quiz progress similarly retains best score and only the latest answers (`backend/services/game_service/data_access/module_quiz_repo.py:114`). A database trigger independently enrolls the module's first tutorial after a completed pre-quiz (`backend/config/database/init/01-schema.sql:679`), so unlock behavior spans Python and SQL.

**Resume is not durable.** Save helpers explicitly discard their `progress` argument and write attempt metadata only; reads return summary fields, while level-list payloads set `progress` to `{}` (`backend/services/game_service/data_access/data_access.py:678`, `:804`, `:838`). There are no tables in the inspected schema for an active simulation snapshot, order/fill history, written plan or reflection. Rooms and engines are process-local, and the last multiplayer disconnect removes the active room and registry entry (`backend/services/game_service/router/router.py:56`, `:572`). This supports no claim of restart-safe or cross-device simulation resume.

Schema/seed files are mounted into PostgreSQL's initialization directory by Compose (`docker-compose.yml:39`). Backend startup merely initializes a pool; the `schema_path`/`initial_state_path` constants are unused and point outside the actual `init/` files (`backend/config/database/postgres.py:7`, `:56`). No tracked migration runner, schema-version table, upgrade sequence or rollback procedure was found. Replaying `CREATE TABLE IF NOT EXISTS` cannot be treated as an upgrade strategy for existing tables. No data conversion should run until migration policy and retained learner records are decided.

## Build, deployment and test evidence

The current Compose file is a development topology: source bind mounts, frontend development port, exposed PostgreSQL port and a host-directory database volume (`docker-compose.yml:1`). The backend image copies the full build context and runs `python main.py`; that entry point enables reload and hard-codes host/port (`backend/Dockerfile:15`; `backend/main.py:6`). No tracked backend `.dockerignore` prevents local credentials, caches or database files entering that context. This is a build-context risk, not evidence that a published image contains secrets. `.env` files are ignored, and the backend specifically ignores `firebase-service-account.json`; ignore rules alone do not constrain Docker COPY. Example credential values are examples, not reported leaked credentials.

Python requirements pin versions but mix runtime, formatting and test dependencies in one list without hashes (`backend/requirements.txt:1`). The source checkout dependencies were not changed. The isolated backend test environment installed this pinned requirements list; no dependency upgrade was requested. Python CI runs a Python 3.13 pytest/coverage job for backend pull requests and `main`/`develop` pushes, with no database service or schema boot test (`.github/workflows/python-tests.yml:1`). Cypress CI starts Firebase Auth emulator and the Vite development server, but no backend/PostgreSQL service (`.github/workflows/e2e.yml:16`). Frontend-only path filtering excludes backend-only changes from that browser job. Neither workflow supplies evidence of a full production build plus real API/database integration.

Inspected tests provide useful regression specifications:

- Auth dependency tests cover missing, invalid, expired, revoked-exception and unverified-email cases; SDK verification is patched (`backend/tests/common/test_auth.py:51`).
- User tests check claim-derived UID/email, ignored forged body identity, validation and collision handling; repository tests use mocked cursors (`backend/tests/services/user_service/test_router.py:64`; `backend/tests/services/user_service/test_data_access.py:78`).
- Game router tests check verified identity, locked/missing quizzes and intentionally public details/leaderboards (`backend/tests/services/game_service/test_router_auth.py:50`). WebSocket tests cover handshake failures, server-stamped identity and single-player level gates (`backend/tests/services/game_service/test_ws_auth.py:121`; `backend/tests/services/game_service/test_ws_level_gate.py:100`).
- Multiplayer tests cover room features, chat/fake-news switches and host reassignment, using patched authentication and fake connections/engines (`backend/tests/services/game_service/test_multiplayer_router.py:16`, `:129`).
- Data-access tests exercise constructed configuration payloads, news/macro windows, tool defaults and level access decisions using mock cursors. They do not execute SQL against PostgreSQL (`backend/tests/services/game_service/test_data_access_level_config.py:31`; `test_data_access_level_gate.py:18`; `test_data_access_news_effects.py:31`; `test_data_access_macro_factors.py:28`; `test_data_access_tools.py:25`, all in that same directory).

Missing evidence includes real database initialization/upgrades, concurrent signup/attempt persistence, cancellation ownership, disconnect/reconnect continuity, authenticated production CORS/WS-origin behavior, and a full-stack browser session against the API. The 209 passing isolated backend tests do not close these integration gaps. V2 setup checks are a separate matter from v1 behavior verification.

## Migration recommendation

Retain verified-identity binding, parameterized persistence, conflict-aware signup, server-side level access checks and the strongest negative tests. Rewrite API projections, persistence and runtime lifecycle around the approved learning and scenario contracts. Drop the public debug clients, fake-news interaction contract, profit-score leaderboard contract and unused resume fiction from the product baseline. Retain old documents only as audit provenance; they contain stale paths and behavior claims (`CLAUDE.md:11`, `:81`; `backend/tests/README.md:32`). A stale checkout instruction described duplicated `_get_level` query columns, but the current SELECT at `backend/services/game_service/data_access/data_access.py:404` and unpack at `:416` each have 15 matching fields; that alleged defect is absent at the audited commit. This correction follows current code rather than old narrative. No user data migration, infrastructure selection or product implementation is approved by this audit.
