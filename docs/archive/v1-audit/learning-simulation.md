# Learning, simulation and rewards audit

V1 contributes useful mission, scenario-playback, progressive-tool and portfolio-analysis concepts. Its curriculum order, completion definitions, scoring and scenario execution cannot be adopted as v2 learning authority. Retain those concepts while rewriting their implementations around the supplied brief.

## Evidence and scope

Source commit: `2bf6b5930858fdbb61bc388d4554d4657d9ce377`. All source citations below refer to paths in the read-only v1 repository `/Users/maahirgarg/Downloads/traders_edge`. Short engine, quiz and analytics filenames are under `backend/services/game_service/service/`; simulator paths are under `backend/market_simulators/`; `02-initial_state.sql` is under `backend/config/database/init/`. [The inventory](learning-inventory.json) assigns a decision and reason to all 36 files owned by this audit and lists seed content by explicit or natural composite ID. A `rewrite` decision retains the identified responsibility or concept, not permission to import its code. No v1 source was edited.

The full backend baseline passed **209 tests in 6.17 seconds**, using an isolated archive of that commit, Python 3.13.0 and the pinned requirements. These tests are useful evidence of existing behavior, not validation against the new brief. Additional isolated probes below reproduced uncovered grading, randomness, accounting and analytics problems without a live database or market download. The live end-to-end game, Yahoo data availability and deployed database were not verified. Curriculum statements in old content are source observations, not independently verified research claims. Existing simulator tests assert immediate historical close fills and orderbook behavior (`backend/tests/market_simulators/yfinance/test_yfinance_simulator.py:70–98`; `backend/tests/market_simulators/orderbook/`). Engine tests cover reservation/cancellation, tool flags, shorts and mission evaluation; portfolio tests exercise mission parameters and rebalance windows (`backend/tests/services/game_service/test_single_player_engine.py`; `test_multiplayer_engine.py`; `test_module5_portfolio_missions.py:147–260`, in that same test directory). Passing those existing tests preserves v1 assumptions; it does not resolve the independently reproduced gaps.

## Assessment and reward contradictions

1. **Completion is not mastery.** Every seeded quiz has `passing_score = 0` (`02-initial_state.sql:4799–4810`). `quiz_service.py:128–182` counts correct answers and declares `score >= passing_score`; it does not require all answers. An isolated probe with one question, zero threshold and `{}` answers returned `score: 0`, `completed: true`. The frontend requires every answer before enabling its submit button; bypassing that client restriction remains possible at the service boundary. Even fully answered, wholly incorrect submissions pass. This is service-level evidence with mocked persistence, not an HTTP integration test.
2. **Pre/post testing encourages recall of the same items.** Module 1 has four pre and four identical post questions; module 2 has six pre and six identical post questions (`:4821–4880`). Module 3 has 8+8, module 4 has 6+6 and module 5 has 8+8. All 16 module-3 answers are option zero (`:4881–4929`; precise question lines are in inventory). Retain feedback and baseline/follow-up measurement; author parallel applications, source basis, confidence and delayed review after the v2 content contract exists.
3. **Only one quiz attempt is allowed.** `quiz_service.py:130–132` rejects attempts after the first. Unlocks depend on quiz/level completion (`:7–37`), so the zero threshold currently conceals the lack of a remedial retry path. Rewrite mastery and remediation together. No specific numeric threshold is chosen by this audit.
4. **Profit and submission are rewarded.** Of 89 missions, 27 use `pnl_at_end`, 17 use `use_order_type`, four use `use_trade_action` and five require excess return over a benchmark/reference. The first module explicitly awards profit milestones (`02-initial_state.sql:1010–1040`); module 2 rewards placing an order on news (`:1042–1056`); module 3.5 requires profit from shorting (`:1530–1551`). Drop those reward dependencies. Outcome P&L and comparisons can remain neutral reflection evidence.
5. **Points directly reward final wealth.** `single_player_engine.py:1231–1265` adds completed mission/bonus points to `net_worth * final_cash_points_multiplier`, then persists the score. This includes starting wealth and seeded positions, not only profits. Module 1 multipliers are zero, but later levels/puzzles enable this component. First two tutorial levels have no passing missions; empty mission lists pass (`:1212–1229`). Neither reaching the end nor scoring high establishes readiness. Tutorial persistence passes `stars=0` with a deprecation comment (`single_player_engine.py:1263`); the reference image's normal/bonus stars are a v2 requirement to design, not evidence of a functioning v1 star system.
6. **Order missions inspect submissions, not decision quality or fills.** `single_player_engine.py:1384–1395` counts logbook entries regardless of final order status; cancelled/unfilled orders can count. Rebalance qualification checks weight movement plus any post-trigger order (`:550–603`), without requiring that order to be filled or to cause the shift. Price drift plus an unrelated submission can meet that proxy. This follows source logic; no complete scenario exploit was executed.
7. **Useful risk concepts still need better measurement.** Eleven missions limit drawdown, seven limit total orders, four cap single-position weight, two cap sector weight, and others examine sectors, correlation, beta or volatility. A maximum-order constraint discourages churn; it is not proof of a written plan or risk recognition. Final portfolio snapshots can also hide earlier concentration (`:1511–1543`). Assess reasoning and adherence over the decision sequence, including choosing not to trade.

There is no plan, maximum-loss explanation, confidence estimate or reflection field in `common/order.py:7–33` or the order registration path (`single_player_engine.py:862–916`). The brief requires these capabilities; they cannot be inferred from existing order-type flags.

## Simulation fidelity and hidden state

**Keep the architectural separation.** The simulator interface publishes fills independently of lesson content (`market_simulators/market_simulator.py:9–112`). The orderbook supports price/time matching, partial quantities and stop variants (`orderbook/orderbook.py:80–139,199–583`). Single-player validates tool access, funds and positions before queuing an order (`single_player_engine.py:842–914`). Short actions have both an explicit tool flag and an exposure cap. These are useful constraints to reimplement, with meaningful tests.

**Historical playback needs a new data and execution contract.** `yfinance/yfinance_simulator.py:55–66` downloads at runtime, discards intraday index times, reindexes to business days and forward-fills. The application rejects daily starts at least 730 days old (`:98–115`), making fixed scenarios age out. This is an application restriction, not a claim about Yahoo's actual retention policy. No cached, versioned data artifact or exchange-session calendar is used by this implementation.

Market orders fill immediately at the already-observed close (`:150–154`); best bid and ask both equal that close (`:294–313`). Historical fills use the entire remaining quantity without volume limits. Limit fills depend on future candle high/low; stops use the adverse extreme, and stop limits may trigger and fill in the same candle without knowledge of intrabar ordering (`:183–272`). There is no explicit commission, borrow-cost or settlement calculation in these fill/accounting paths. Orderbook depth can create spread, partial fills and price impact, but that does not make historical and synthetic modes equivalent or comprehensively realistic.

**Two historical scenarios have insufficient rows for their configured duration.** `module-1.3` has ten ticks but its `2025-01-02` through `2025-01-10` range produces seven business-day rows; `module-1.4` has 12 ticks but `2025-09-29` through `2025-10-10` produces ten (`02-initial_state.sql:59–91,572–573`). Reproducing the implementation's `pandas.bdate_range` confirmed those counts. `_get_market_OCHL` raises when the tick is outside the frame (`yfinance_simulator.py:135–137`) and the engine ticks until configured total (`single_player_engine.py:46–47,740–745`), so the configuration permits exhaustion before completion. A real download/playthrough was not run.

**Seeded does not mean isolated or reproducible across concurrent sessions.** `orderbook_simulator.py:42–48` calls global `random.seed` and `np.random.seed` only when seed is truthy; seed zero is treated as absent. Price noise and order sizes then consume global generators (`:98,215,245,254`), while the local `self.rng` is unused. In the isolated archive, seed-7 simulator A produced closes `[99.77,100.07,99.83,99.79,100.07]`; constructing an otherwise unused seed-99 simulator B before A's replay changed them to `[99.82,99.92,100.02,99.89,99.65]`. Require isolated per-scenario/ticker generators, versioned inputs and scheduling semantics before claiming reproducible evaluations.

**Future hiding is partial.** Single-player game-start strips `news`, `news_effects` and `macro_effects` (`single_player_engine.py:712–717`) and publishes only current-tick news/effects during play (`:754–807`). Keep that separation. It is undermined by the raw level-detail API described in the platform audit, which returns schedules/parameters through another route. Real ticker identities, historical dates and seeds are also included in configuration. Future hiding must be enforced across every public response; a single sanitized event is insufficient.

## Progression and rewards

Daily activity is recorded on completed levels, using server-local `date.today()` (`progression_service/service/daily_activity_service.py:15–22`; `single_player_engine.py:1268–1276`). Streak calculation counts consecutive distinct active dates through today/yesterday (`daily_activity_service.py:25–43`). This is closer to a learning streak than an order-count streak, but the current completion rule can still reward profit/submission and repeat attempts inflate raw activity counts. Retain optional learning continuity; define user-day/timezone, idempotency and eligible learning events.

The seven achievement IDs describe first/five/ten levels, modules 1/2, puzzle unlock and endless unlock. Several descriptions assert trading skill or mastery merely from finishing levels (`02-initial_state.sql:4782–4788`). The puzzle hint says all Adventure modules, while actual puzzle access checks `module-1.4` completion (`game_service/data_access/data_access.py:687–773`); a prerequisite cannot be established by its label. The tracked backend reads achievement ownership but contains no grant write or achievement-award trigger (`backend/services/progression_service/data_access/achievements_repo.py:7–31`; `backend/config/database/init/01-schema.sql:625`). The seed comment promising runtime population is not an implemented award mechanism. User total points aggregate level `best_points` (`backend/services/user_service/data_access/data_access.py:97–108`); there is no separate verified XP/rank system. Endless is not a working mode in the frontend route inventory. Do not report cosmetic catalogs, global rank or mastery rewards as implemented solely because the reference image shows them.

The leaderboard ranks stored best points (`game_service/data_access/data_access.py:781–785`), which inherit final-wealth scoring. Multiplayer returns final net worth per user (`multiplayer_engine.py:1090–1100`), not a verified learning-process ranking. Replace these reward inputs; retain progress visibility and optional process-based competition only after approved mastery prerequisites.

## Migration boundary and unresolved contracts

Keep the concepts of guided missions, hands-on scenarios, tool prerequisites, explanatory feedback, learning activity and portfolio comparisons. Rewrite lesson/assessment sources and sequencing, the public/private scenario split, deterministic playback, order/accounting events, plan-before-action and reflection, progression evidence and rewards. Drop profit/alpha goals as mastery criteria, order-submission rewards, unverified skill claims and pressure-driven trading copy. The file inventory makes implementation disposition explicit.

Phase 2 must define the shared lesson/scenario/badge contracts, provenance/seed/friction/hidden-state rules, mastery and remediation, historical-data rights, localization, and plan/reflection evidence. This audit introduces no parallel content runtime format, new curriculum lessons or product UI. Design selection, technical/safety review and separate implementation approval remain gates.
