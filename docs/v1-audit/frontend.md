# Frontend audit

The useful inheritance is the separation of route, simulation transport, portfolio views and guided missions. The existing screens and wire contracts need a rewrite for the foundations-first curriculum, explicit trade plans, mobile accessibility and process-based assessment. The reference image is a content/mechanics brief, not evidence that its screens or appearance already exist.

## State, identity and contracts

- **Authentication has a sound starting distinction.** `useAuth.ts:29–32,69–76` only treats 404 as missing onboarding. However, other failures clear the app user and leave no recoverable error in the exported state (`:98–106`); protected routes then send the user to sign-in. The asynchronous auth callback has no generation/cancellation guard against an older profile load finishing after sign-out/account switch (`:56–79`). Retain the concept, rebuild the state machine.
- **The level popup violates hook ordering.** `frontend/src/features/levels/components/LevelDetailPopup.tsx:16` returns for a null selection before `useNavigate`, three state hooks and an effect (`:19–26`). Selection changes therefore alter which hooks execute in this component. Move the null guard below hooks or split the mounted detail child; do not assume the existing navigation tests prove this safe. This is a static correctness finding, not a reproduced browser failure.
- **Deep-link intent is lost.** `ProtectedRoute.tsx:12–17` stores `state.from`, but `AppRoutes.tsx:20–28` sends authenticated users to `/dashboard`, and `UsernameSetup.tsx:34–35` does the same. The login comment promising the original route is not implemented by these paths.
- **HTTP bearer refresh is implemented.** `frontend/src/services/apiClient.ts:23–55` fetches a Firebase token per request and retries one 401 with forced refresh. Keep that policy. Rewrite runtime decoding/error types: `:58–67` casts arbitrary JSON, `:37–45` sends authorization even to an absolute caller-supplied URL, and `:3–9` falls back to HTTP regardless of page protocol. No untrusted absolute-URL caller was established; this is an API boundary hazard, not a demonstrated leak.
- **Access gates are UX, not authorization.** `useLevelAccessGate.ts:43–67` reads server availability and collapses network/auth failure into denied. Single-player mounts its trading child only when allowed (`SinglePlayerTradingPage.tsx:36–44`). Quiz does not defer its fetch: `QuizPage.tsx:57–100` runs independently of the render guard at `:161–162`, contrary to its comment at `:26–28`. Gate by the actual quiz ID and show outage/retry separately from prerequisite explanations.
- **Quiz drafts are memory-only.** `QuizContext.tsx:21–44` holds answers/submission keyed by quiz ID. `QuizPage.tsx:72–87` reconstructs previous attempts and locks them as submitted. Client `allAnswered` disables submission (`:355–360`), but this is not proof of server mastery enforcement. Learning audit confirms zero pass thresholds in seeded quizzes; rewrite the contract, not only the button.
- **Transport boundaries exist, validation is permissive.** `gameSocket.ts:65–100` dispatches a mixture of enveloped events and bare order responses after shallow checks, logs raw payloads and swallows parse errors. `:122–124` silently discards sends on a closed socket. `useSinglePlayerGame.ts:73–102` handles a locked-level close specially, but provides no general reconnect/backoff or surfaced failure path for other closes. Multiplayer has separate connection/error state (`MultiplayerSessionProvider.tsx:142–161`). Neither is evidence of reliable interrupted-session recovery.
- **Resume is not a persisted simulation.** `LevelDetailPopup.tsx:55–74` presents Resume/Start and sets `newGame`; `SinglePlayerTradingPage.tsx:49–51` passes an `isResuming` flag. Both send the same level/mode start payload (`useSinglePlayerGame.ts:94–98`). Backend inspection reconciles this with always-fresh initialization (`backend/services/game_service/service/single_player_engine.py:95–119`): preserve explicit restart/resume requirements, not the existing promise.
- **Presentation helpers blur invalid and absent state.** `tradingPayloadMappers.ts:54–67` defaults unknown order types to Market; `:203–231` coerces tool values with `!!` and defaults absent tools to an enabled subset; `:283–325` requires net worth to show a result and defaults score fields to zero. Rewrite with versioned validated messages and distinct unknown/error states. Keep order IDs and partial-fill presentation concepts (`:417–428`; `useTradingSessionState.ts:1873–1899`).
- **Portfolio state is separated but not authoritative accounting.** `usePortfolioState.ts:42–55` derives displayed net worth/P&L from client state. `useTradingSessionState.ts:1220–1297` resets many independent state cells. Rebuild coherent snapshot/event handling and reconcile against server balances; do not port the large hook as a new financial ledger.

## Safety and content conflicts

1. **There is no written plan in an order.** `gameSocket.ts:142–158` sends ticker/type/action/quantity/prices; `TradeModal.tsx:107–110,162–179` collects and validates order values only. `TradingPage.tsx:420–470` directly submits after order checks. Require a stored plan, maximum-loss reasoning and review before simulated execution; do not reward submission itself.
2. **Profit-based scoring is active presentation.** `GameEndPointsSection.tsx:24–35` shows final-cash points alongside mission points. `LevelDetailPopup.tsx:93–119` ranks per-level scores. Learning audit confirms the engine's net-worth-derived scoring. Drop this reward/leaderboard basis; retain neutral outcome analytics as evidence for reflection.
3. **Countdown pressure is implemented.** `TradingRightPanel.tsx:188–199` supplies 180 seconds and a 60-second threshold; `CountdownTimer.tsx:59–69` emits a danger “1 minute left” toast. Drop the timer/forced-next-turn UX. This is not a missing mock feature.
4. **Confetti is on level completion, not order execution.** `GameEndModal.tsx:116–125` only renders it when passed, alongside a net-worth count-up (`:67–99,130–131`). Do not exaggerate this as order confetti. Drop the old reward spectacle and financial-success emphasis; any future restrained learning celebration needs its own design/safety review and reduced-motion behavior.
5. **Multiplayer has no client mastery prerequisite.** `GamesSection.tsx:13` and `AppRoutes.tsx:58–61` expose it for authenticated users. Platform audit confirms no server mastery gate. Room access must not precede readiness checks.
6. **Tutorials are tool walkthroughs, not a complete curriculum.** `frontend/src/features/tutorials/registry/tradingTutorialRegistry.ts` contains 23 definitions and 122 steps. Useful passages distinguish probability from certainty (`:177–180`) and explain drawdown (`:215–232`). But the opening walkthrough teaches chart/timer/buy/sell (`:77–143`), and action-gated order steps (`:1063–1069`) do not assess a written plan. Rewrite content into the later shared lesson contract with source basis and learning objective; keep no parallel runtime format now.

They have no established license/provenance in this audit. Drop the old mode artwork/logo from the redesign; redraw the educational candle illustration with an accessible text equivalent after content/design approval. Lucide achievement names/fallbacks are mapped in `achievementIconService.ts:17–34`; retain the mapping concept, not legacy achievement criteria or visual language.

`frontend/package.json:12–47` includes React/Vite/TypeScript, Firebase, Tailwind, MUI/Emotion, two chart stacks, a calendar, loaders, toast and confetti. Do not carry the full dependency graph forward automatically. Reassess each dependency against approved UI needs; remove confetti and avoid carrying two chart libraries without a concrete requirement. Existing frontend deployment files/configuration are environment-specific references, not v2 release settings.

There are four Cypress specifications with **16 `it` cases**: auth/onboarding and access gates; dashboard/module navigation; profile achievements; multiplayer no-NPC order UI. They use intercepted API data and the Firebase emulator sign-in bridge (`tests/cypress/support/e2e.js:7,47–55`; `src/services/firebase.ts:48–57`); the multiplayer suite additionally mocks WebSocket. Thus these are useful behavioral examples, not proof of real backend integration. `package.json:6–10` has no test script. No tracked unit tests cover mappers/calculations, and no mobile/a11y assertions were found in these specs. V2 needs targeted tests for contract rejection, stale auth, reconnect/resume, prerequisite errors, plan gating, non-profit rewards and keyboard/390px operation once implemented.

## Reconciled cross-area findings

- The frontend's Resume label initially suggested stored simulation recovery. Comparing its identical start payload with the engine's unconditional initialization disproves that interpretation. Both audits treat recovery as a new requirement.
- A client `allAnswered` check and pre/post quiz route gates initially suggest assessment control; seeded zero pass thresholds and backend grading show they do not establish mastery. Keep server-enforced prerequisites, replace the completion definition.
- Tool flags are not uniformly cosmetic: the learning audit confirms single-player enforcement (`backend/services/game_service/service/single_player_engine.py:842–860,886–893`). Multiplayer presentation toggles require a separate enforcement decision; do not generalize the single-player guarantee.
- The platform audit corroborates absent multiplayer mastery, while the learning audit corroborates cash-based points. These are cross-layer changes, not isolated UI copy edits.

Before implementation, resolve the shared v2 lesson/scenario/assessment contracts, auth/session policy, interruption semantics and server-owned progression. Owner design selection and separate implementation approval remain required.
