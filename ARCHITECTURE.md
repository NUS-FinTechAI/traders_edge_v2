## Three architectural decisions (target)

1. **Keep a modular monolith.** Retain React/Vite, FastAPI, SQLAlchemy and ordered migrations; no microservices or framework churn. Evolve the existing content, learning/progression, simulation and identity modules. Add assessment, reward/inventory and optional competition responsibilities behind internal boundaries, not separate infrastructure.
2. **Make authored learning and server-owned evidence primary.** A level is a learning experience with objectives, typed steps and verifiable missions; it is not a sandbox session or a renamed prose lesson. A diagnostic measures baseline without blocking learning; a separate postcheck establishes mastery. XP/player level, mastery and multiplayer process-rank are distinct concepts.
3. **Preserve history through versioned, additive contracts.** Pin new attempts to immutable content/rubric/scenario versions. Preserve legacy attempts, responses, completion and XP. Every new scoring/progression command must replay the same committed response on a same-key retry, not merely avoid a second reward.

### Authoritative ownership

- **Identity/profile:** backend binds all reads/writes to the authenticated learner; clients cannot submit another user's identity or set XP, mastery, stars, inventory or rank. Public leaderboard projection exposes only opted-in pseudonyms and permitted learning totals.
- **Content:** server-private curriculum catalog owns objectives, prerequisites, ordered teaching/bonus steps, assessment forms, rubric versions, sources and the bounded lesson-simulation binding. Extend its validated contract rather than invent a parallel runtime format. Finite cosmetic reward policy remains code-owned in `rewards.py`, not catalog-authored. Client receives only the current permitted public projection.
- **Learning/assessment:** backend owns run position, submitted answers, first-attempt identity, feedback, required/bonus mission evidence, completion, review scheduling and mastery decisions. Progression consumes assessed evidence, not page visits or a client “complete” flag.
- **Simulation:** engine owns seed, hidden path, clock, portfolio, fills and command history. Authored mission adapters constrain permitted actions and produce process evidence; the general sandbox remains separate. A written plan is required before every simulated trade, including sells; valid length/presence is not quality.
- **Rewards:** unique learning-event XP, projected completion stars and saved finite cosmetic grants are implemented. The cosmetic policy is code-owned in `rewards.py`, not catalog-authored. Player-level projection and a multiplayer process-rank ledger remain **proposed**, with no profit/volume/order-count inputs permitted. Client owns transient presentation only; drafts must not become grading authority.

## Proposed entities and lifecycle

The table describes the **full target domain**, not a table-per-entity implementation or a claim that every feature is delivered. The implemented decision-practice subset and actual routes are identified below. Existing `Attempt`, `XPLedger`, `ReviewItem` and other models remain in use.

Bounded implementation decision: levels, steps, mission criteria and assessment forms are authored in the existing canonical catalog, not separate mutable tables or a parallel content format. Migration 3 added only `learning_runs` and an immutable run-command ledger; each accepted answer command retains the evidence needed to distinguish first response from later retries. Malformed inputs and gate failures do not create learning evidence. Reuse existing completion, mastery, review and XP records. Do not create a table or service for every conceptual noun below. Cosmetic grants/equipment now form a separate migration-4 slice; competition remains proposed, not implied by either schema extension.

Returning learners resume the exact active step/feedback, not merely the first incomplete lesson. Profile, dictionary and leaderboard are side trips that preserve the active task. Modes are Adventure learning, Quiz/review, Multiplayer and Endless; locked modes explain prerequisites. Advanced content remains optional after the foundations-first core.

## Persistence, retries and content boundaries

**Migration 3:** `server/app/migration_v3.py` adds the two run/command tables without changing migrations 1/2 or old learner records. New runs pin private tasks, keys, rubric, approval state, review interval and content version. Legacy attempts keep their original unversioned data; no baseline, bonus or content provenance is invented. Maps label retained completion as `legacy`, and existing event keys prevent duplicate XP. The populated-v2 upgrade test verifies retained records and exactly two added tables. **Migration 4** adds only `reward_grants`, `reward_commands` and two nullable profile equipment columns, preserving migrations 1–3 and populated learner evidence. The upgrade regression seeds all 14 prior data tables, including saved simulation state/commands, and compares every original column and full rowset before and after upgrade and repeat migration. Delayed reviews and reciprocal lesson/session bindings use existing JSON/run tables, not new tables. Future release archives and competition still require reviewed contracts/migrations. Back up persistent databases before upgrades. Strict schema checks mean an old binary is not an automatic rollback: use a compatible release or tested restore, not destructive down-migrations.

**Same-response retry contract:** learning already stores `Attempt.result` and simulation stores `SimulationCommand.response` (`server/app/learning.py::submission_replay` and `submit`; `server/app/simulation/api.py::SimulationCommand`, `start` and `execute`). Same authenticated learner + key + canonical operation/target/payload returns the originally committed body, including its original XP delta and profile snapshot, even if current progress changed. A changed payload under that key returns 409. New run commands implement this invariant before resolving current content, prerequisites or pinned rubric compatibility. Their canonical request hash binds the operation, target and normalized payload; the run snapshot separately pins content/rubric versions. Evidence, progress, rewards and the replay response commit atomically under uniqueness constraints and existing transaction/ownership locks. Persist pending client command/key across reloads; retry a lost response with that same key, but a deliberate new answer is a new attempt/key. Fresh profile state is fetched separately, not substituted into a replay. Ordinary simulation and bound bind/review commands also replay before fresh gates and saved-version checks. Fresh bound audits require the latest `observation_token`, which hashes only public observed engine state and changes after same-tick order placement/cancellation. Historical committed tokenless audits retain their original request hashes and replay; `StepAnswer` serialization is unchanged. Reward commands have a separate namespace and replay before current policy/publication checks. Equipment replay returns the old response without reapplying old state. Do not describe all current mutations (for example journal creation) as idempotent.

**Content/public boundary:** extend existing content validation with objective/source references, immutable IDs/versions, step types, acyclic prerequisites, reachable required missions, rubric/reward rules and review status. Record source URL/section, review date, jurisdiction scope and scenario provenance (synthetic generator or permitted historical dataset, license, seed, engine version and friction assumptions). Keep localization packs separate from the jurisdiction-neutral core. Source metadata and validation do not prove correctness; independent financial/pedagogical review is still required.

Keep answer keys, unearned feedback, private rubrics, hidden future prices, seeds that reveal future paths and opponent-private state out of public catalog payloads, browser bundles, analytics and logs. Reveal only submitted-item feedback at the permitted phase and observed scenario history; debrief must not expose reusable future answers accidentally. Preserve the public projections in `server/app/learning.py`, `server/app/learning_runs.py` and `server/app/simulation/engine.py`; test nested task fields as well as the top-level response. Never send the private catalog or raw simulation snapshot to the client.

## Evaluation and privacy

Existing analytics is an opted-in daily aggregate of newly rewarded learning events, not a learning-gain study (`server/app/progression.py::reward`). Legacy whole-set grading produces attempt-level Brier feedback without a reward change (`server/app/learning.py::submit`); interactive runs save optional confidence but do not report a Brier summary. These cannot establish baseline-to-post learning gain or delayed transfer by themselves.

Proposed evaluation records purpose, immutable item/form/content/rubric version, first response before feedback, attempt number, correctness, optional confidence, pre/post pairing and scheduled/actual review delay. Preserve wrong and missing responses; distinguish retries, prior exposure, completion and attrition from first-attempt performance. Use equivalent independently reviewed post/delayed forms and unfamiliar scenarios; report calibration and risk/process outcomes, not profitability. Process metrics require structured, rubric-verifiable evidence; if written reasoning has no validated assessment, label it unassessed rather than infer quality from text length.

Separate necessary operational attempt/resume data from optional research analytics. Keep analytics consent off by default and separate from leaderboard consent; refusal must not impede learning. Minimize exports to pseudonymous IDs and derived measures, exclude journal/plan text, account details and hidden scenario state. Define retention/deletion windows, access controls, withdrawal/export handling and small-cohort suppression before collecting new research events. Those privacy policies and paired evaluation storage are target work, not existing guarantees.
