# Workflow architecture

## Scope and evidence

Goal: deliver the complete beginner-learning workflow, not a simulator with prose lessons attached. The merged backend supports all ten modules’ decision-practice runs, one lesson-bound simulation, shared AI challenges/bosses, daily game economy and supplementary/classroom quizzes. Frontend integration and the complete product workflow remain unfinished. This document separates inspected implementation from proposed contracts. Independent technical/safety review approved the bounded backend contract below; financial content accuracy, publication and production readiness remain unapproved. A teammate owns frontend visual design. Backend delivery prioritizes v1 content mapping, authored teaching/assessment contracts and durable state rather than further visual prototypes.

Source precedence: the owner-selected [gameplay brief](docs/source/traders-edge-game-design-brief.txt) governs conflicting gameplay requirements under [ADR 0003](docs/decisions/0003-gameplay-brief-authority.md). The preserved [supervisor summary](docs/source/traders-edge-supervisor-summary.md) supplies curriculum, assessment, safety and evaluation goals; the [screen reference](docs/source/Trader_s_Edge_Sample_UI.jpg) specifies screen content/mechanics rather than styling. The owner's workflow adds explicit diagnostic/exit-check separation. Benchmark Duolingo/Brilliant for short interactive teaching, worked examples, predictions, corrective feedback and retrieval—not branding, visual imitation or claims of equivalent efficacy. The read-only sibling v1 repository `traders_edge` is discovery material, not evidence of v2 implementation.

## Three architectural decisions (target)

1. **Keep a modular monolith.** Retain React/Vite, FastAPI, SQLAlchemy and ordered migrations; no microservices or framework churn. Evolve the existing content, learning/progression, simulation and identity modules. Add assessment, reward/inventory and optional competition responsibilities behind internal boundaries, not separate infrastructure.
2. **Make authored learning and server-owned evidence primary.** A level is a learning experience with objectives, typed steps and verifiable missions; it is not a sandbox session or a renamed prose lesson. A diagnostic measures baseline without blocking learning; a separate postcheck establishes mastery. XP/player level, learning mastery and competitive game outcomes/rating are distinct concepts.
3. **Preserve history through versioned, additive contracts.** Pin new attempts to immutable content/rubric/scenario versions. Preserve legacy attempts, responses, completion and XP. Every new scoring/progression command must replay the same committed response on a same-key retry, not merely avoid a second reward.

### Authoritative ownership

- **Identity/profile:** backend binds all reads/writes to the authenticated learner; clients cannot submit another user's identity or set XP, mastery, stars, inventory or rank. The learning leaderboard exposes only opted-in pseudonyms and permitted learning totals; competitive standings require their own reviewed public projection.
- **Content:** server-private curriculum catalog owns objectives, prerequisites, ordered teaching/bonus steps, assessment forms, rubric versions, sources and the bounded lesson-simulation binding. Extend its validated contract rather than invent a parallel runtime format. Finite cosmetic reward policy remains code-owned in `rewards.py`, not catalog-authored. Client receives only the current permitted public projection.
- **Learning/assessment:** backend owns run position, submitted answers, first-attempt identity, feedback, required/bonus mission evidence, completion, review scheduling and mastery decisions. Progression consumes assessed evidence, not page visits or a client “complete” flag.
- **Simulation:** engine owns seed, hidden path, clock, portfolio, fills and command history. Authored mission adapters constrain permitted actions and produce process evidence; the general sandbox remains separate. A written plan is required before every simulated trade, including sells; valid length/presence is not quality.
- **Rewards:** learning XP/stars and finite learning-earned grants remain distinct from login and challenge game rewards. `economy.py` owns currency rules and shop policy; profile projection derives player level from total XP. ADR 0003 permits net-profit game outcomes while excluding individual order-count/volume rewards and claims that profit measures learning. Public Elo rating follows the separately versioned multiplayer policy and is not a competence score. Client drafts never become grading or reward authority.

## Proposed entities and lifecycle

The table describes the **full target domain**, not a table-per-entity implementation or a claim that every feature is delivered. The implemented decision-practice subset and actual routes are identified below. Existing `Attempt`, `XPLedger`, `ReviewItem` and other models remain in use.

Bounded implementation decision: levels, steps, mission criteria and assessment forms are authored in the existing canonical catalog, not separate mutable tables or a parallel content format. Migration 3 added only `learning_runs` and an immutable run-command ledger; each accepted answer command retains the evidence needed to distinguish first response from later retries. Malformed inputs and gate failures do not create learning evidence. Reuse existing completion, mastery, review and XP records. Do not create a table or service for every conceptual noun below. Cosmetic grants/equipment form the migration-4 slice; migrations 5–10 append shared AI challenges, economy, chapter access, quiz rooms/attempts, shared multiplayer and research metadata/receipts. The target table retains broader authoring/evaluation concepts that are not implied by these tables.

## Persistence, retries and content boundaries

**Migration 3:** `server/app/migration_v3.py` adds the two run/command tables without changing migrations 1/2 or old learner records. New runs pin private tasks, keys, rubric, approval state, review interval and content version. Legacy attempts keep their original unversioned data; no baseline, bonus or content provenance is invented. Maps label retained completion as `legacy`, and existing event keys prevent duplicate XP. The populated-v2 upgrade test verifies retained records and exactly two added tables. **Migration 4** adds only `reward_grants`, `reward_commands` and two nullable profile equipment columns, preserving migrations 1–3 and populated learner evidence. The upgrade regression seeds all 14 prior data tables, including saved simulation state/commands, and compares every original column and full rowset before and after upgrade and repeat migration. Delayed reviews and reciprocal lesson/session bindings use existing JSON/run tables, not new tables. Migrations 5–8 append AI challenge attempts/commands, game economy, common chapter/daily definitions, chapter access/boss evidence and quiz rooms/attempts. Migration 9 appends multiplayer lobby/member/command/queue/rating/throttle tables; migration 10 appends study metadata and receipts. Broader content-release archives and participant lifecycle still need their contracts. Back up persistent databases before upgrades. Strict schema checks mean an old binary is not an automatic rollback: use a compatible release or tested restore, not destructive down-migrations.

**Same-response retry contract:** learning already stores `Attempt.result` and simulation stores `SimulationCommand.response` (`server/app/learning.py::submission_replay` and `submit`; `server/app/simulation/api.py::SimulationCommand`, `start` and `execute`). Same authenticated learner + key + canonical operation/target/payload returns the originally committed body, including its original XP delta and profile snapshot, even if current progress changed. A changed payload under that key returns 409. New run commands implement this invariant before resolving current content, prerequisites or pinned rubric compatibility. Their canonical request hash binds the operation, target and normalized payload; the run snapshot separately pins content/rubric versions. Evidence, progress, rewards and the replay response commit atomically under uniqueness constraints and existing transaction/ownership locks. Persist pending client command/key across reloads; retry a lost response with that same key, but a deliberate new answer is a new attempt/key. Fresh profile state is fetched separately, not substituted into a replay. Ordinary simulation and bound bind/review commands also replay before fresh gates and saved-version checks. Fresh bound audits require the latest `observation_token`, which hashes only public observed engine state and changes after same-tick order placement/cancellation. Historical committed tokenless audits retain their original request hashes and replay; `StepAnswer` serialization is unchanged. Reward commands have a separate namespace and replay before current policy/publication checks. Equipment replay returns the old response without reapplying old state. Do not describe all current mutations (for example journal creation) as idempotent.

**Content/public boundary:** extend existing content validation with objective/source references, immutable IDs/versions, step types, acyclic prerequisites, reachable required missions, rubric/reward rules and review status. Record source URL/section, review date, jurisdiction scope and scenario provenance (synthetic generator or permitted historical dataset, license, seed, engine version and friction assumptions). Keep localization packs separate from the jurisdiction-neutral core. Source metadata and validation do not prove correctness; independent financial/pedagogical review is still required.

Keep answer keys, unearned feedback, private rubrics, hidden future prices, seeds that reveal future paths and opponent-private state out of public catalog payloads, browser bundles, analytics and logs. Reveal only submitted-item feedback at the permitted phase and observed scenario history; debrief must not expose reusable future answers accidentally. Preserve the public projections in `server/app/learning.py`, `server/app/learning_runs.py` and `server/app/simulation/engine.py`; test nested task fields as well as the top-level response. Never send the private catalog or raw simulation snapshot to the client.

## Evaluation and privacy

Existing analytics is an opted-in daily aggregate of newly rewarded learning events, not a learning-gain study (`server/app/progression.py::reward`). Legacy whole-set grading produces attempt-level Brier feedback without a reward change (`server/app/learning.py::submit`); interactive runs save optional confidence but do not report a Brier summary. These cannot establish baseline-to-post learning gain or delayed transfer by themselves.

Proposed evaluation records purpose, immutable item/form/content/rubric version, first response before feedback, attempt number, correctness, optional confidence, pre/post pairing and scheduled/actual review delay. Preserve wrong and missing responses; distinguish retries, prior exposure, completion and attrition from first-attempt performance. Use equivalent independently reviewed post/delayed forms and unfamiliar scenarios; report calibration and risk/process outcomes, not profitability. Process metrics require structured, rubric-verifiable evidence; if written reasoning has no validated assessment, label it unassessed rather than infer quality from text length.

Separate necessary operational evidence from optional study enrollment and daily aggregate analytics. `research.py` provides three authenticated owner downloads: learning runs, completed learning attempts and AI challenges. They retain own submitted rationale and observed timing while excluding answer keys, unseen tasks, hidden prices and opponent-private state; they do not export standalone simulation, quiz or multiplayer records. Enrollment defaults off and requires the exact configured policy/version/digest, with separate withdrawal and frozen first prior-knowledge reports. Analytics opt-in never implies study consent. No instructor/researcher can use this API to retrieve another owner's exports. Future cohort analysis must define approved access, minimization, retention/deletion and small-cohort suppression; account deletion, cohort exports and paired evaluation remain absent.
